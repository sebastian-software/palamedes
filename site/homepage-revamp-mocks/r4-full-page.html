01 · Clear — Developer Experience

Write the message where the UI happens.

No message-ID bookkeeping, no parallel dictionary files. Messages are identified by message + context — stable across refactors and years of catalog history. getI18n() resolves the active instance in server components, client islands, and backend handlers alike.

03 · Fast — Performance

Every extract finishes faster than a blink.

A full extract and catalog update over 1,500 files takes 83.89 ms — 29× to 79× faster than every tool we measured doing the same job. (The one tool that skips catalog updates entirely is still 5.7× slower.) Touch five files and re-run: 33 ms, because unchanged files are neither read nor parsed.

04 · Why this holds

Speed, scope, and DX fall out of one decision.

One semantic model (message + context), one catalog engine (ferrocat, in Rust), one runtime contract (getI18n()), and adapters kept deliberately thin. Nothing is duplicated, so nothing drifts — and the native core does the careful work once. The full reasoning is public: 25 ADRs, including the ones about what Palamedes refuses to do.

06 · Who builds this

Third-generation tooling, not a weekend take.

Palamedes is maintained by Sebastian Software GmbH. It is the third generation of source-string-first i18n tooling from the same author — from gettext-style macro systems in qooxdoo to a full enterprise Lingui migration at Regrello (acquired by Salesforce in 2025). The lessons are written down as 25 ADRs before you depend on the tool.

What Palamedes doesn't do

No TMS, no machine translation, no hosted dashboard. Palamedes covers the complete local workflow; Palamedes+ is a planned optional managed layer — the open-source core needs no account and stays complete without it.

08 · Questions

Asked before adopting.

Do I need an account or a cloud service?
No. The toolchain is MIT-licensed, runs locally, and catalogs live in your repository. Palamedes+ is a planned optional layer — nothing requires it.
Does it work with my framework?
First-party adapters cover Next.js, TanStack Start, SolidStart, Waku, React Router, Remix v3 (preview), and Vite — plus Hono and Express on the backend. Each combination is a verified example app, not a claim.
Is it production-ready?
Recommended for new projects. Stability tiers and public API expectations are documented; preview surfaces are labeled as such — including on this page.
How does migration from Lingui work?
A step-by-step playbook covers it. Source-string-first .po catalogs are often reusable after one extraction pass; explicit-ID setups need cleanup first.
What do translators work with?
Plain .po files they can read, diff, and review — no proprietary format. Teams can opt into FCL for canonical, merge-friendly generated catalogs.
Can AI coding assistants use it?
Yes — point them at llms.txt: the whole API surface in one machine-readable file, served from palamedes.dev.
