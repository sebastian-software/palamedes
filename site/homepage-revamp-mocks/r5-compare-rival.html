The same idea, on an engine 29.57× faster.

Lingui got the authoring model right, and we are not going to pretend otherwise — write the message where the UI happens, let the source string be the identity, keep catalogs translators already know. Palamedes agrees with every part of that, then replaces the machinery underneath: one Rust core instead of a JS plugin stack, one runtime access model instead of several.

Our position

If you already believe in macro-based authoring and .po catalogs, the argument is not about the model — you and Lingui and we all agree on it. The argument is about what runs it.

01 — The verdict, first

Ten seconds, honestly.

Pick Lingui if
  • You need Vue or React Native. Palamedes has neither and will not fake it.
  • Your catalogs depend on explicit custom IDs — Palamedes deliberately offers no second identity convention.
  • You want a decade of production history over a younger toolchain.
Pick Palamedes if
  • You want the same authoring model on a native engine — 29.57× faster on the checked, re-runnable benchmark.
  • You want one runtime call — getI18n() — across server components, client islands, and backend handlers.
  • You want semantic .po merges and machine-readable audits as CI gates, not plugins.
02 — Credit & cost

What Lingui earned — and what that history costs you.

What Lingui earned
  • Macro-based authoring, source-derived identity and native PO catalogs form a coherent client-to-catalog workflow.
  • Genuinely broad framework support: React, React Native, Vue 3, SolidJS and vanilla JS are first-party, not community ports.
  • Native ICU MessageFormat and first-class .po catalogs, so translator tooling works without adapters.
What that history costs
  • v6 was a hard cut — ESM-only, Node ≥22.19, YAML config removed, a changed auto-ID encoding that forces manual catalog rewrites.
  • Breadth thins out per target: Astro requested since 2023, still not first-party; the App Router dynamic-route extraction limitation open since 2025.
  • The performance ceiling is architectural — worker threads and an experimental Rolldown extractor chase a constraint a native core does not have.
03 — What is actually different

Three decisions, not thirty features.

One runtime model, not several entry points

Exactly one way for transformed code to reach the active instance: getI18n(). The same call works in a Next.js server component, a Solid island, and an Express handler — the runtime chapter of your onboarding doc is one paragraph long.

Catalog semantics in one native engine

Parsing, updating, auditing, ICU diagnostics and compilation live in one Rust core, not spread across JS plugins. The speed is the visible consequence; the useful one is that audit results cannot depend on which side of the toolchain asked.

One identity convention, permanently

Lingui lets you choose between source-derived and explicit IDs. Palamedes refuses the second path on purpose: one fewer decision at the start, one fewer schism at year three.

04 — In code

Authoring barely changes. That is the point.

Lingui
import { t } from "@lingui/core/macro"

function checkoutLabel(seats) {
  return t`Buy ${seats} seats`
}
Palamedes
import { t } from "@palamedes/core/macro"

function checkoutLabel(seats) {
  return t`Buy ${seats} seats`
}

If your Lingui code already avoids explicit IDs, most of it reads identically after the import swap. Your components are not the migration — the catalogs and the runtime wiring are, and the playbook covers both.
