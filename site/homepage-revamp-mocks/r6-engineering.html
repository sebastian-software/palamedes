How it actually works

“Written in Rust” is the boring half.

Rust buys speed; it doesn’t buy architecture. The interesting part is what Palamedes refuses to do at runtime — parse, guess, or duplicate — and the machinery that makes those refusals stick. Nine mechanisms, each with the decision record that explains it.

01 — Compiled, not interpreted

Your translations become code. No parser ships to production.

Most i18n runtimes ship an ICU parser to every visitor and interpret message syntax on the fly. Palamedes compiles catalogs into executable message functions at build time — plurals become plain functions, and the production runtime contains no parser at all.

What you write — de.po
msgctxt "checkout"
msgid "{seats, plural, one {# seat left}
  other {# seats left}}"
msgstr "{seats, plural, one {Noch # Platz}
  other {Noch # Plätze}}"
What ships — compiled artifact (illustrative)
// generated — executable message function
export const m_checkout_seats =
  (v) => plural(v.seats, {
    one:  `Noch ${v.seats} Platz`,
    other:`Noch ${v.seats} Plätze`,
  })

Sketch, not literal output — the shape is the point: message syntax is resolved before deploy, not in your visitor's browser.

02 — The cache that trusts stat

Unchanged files are neither read nor parsed.

Extraction keeps a per-file cache validated by a filesystem stat: if a file's identity hasn't changed, its messages are reused without opening it. Files that do change are parsed in bounded parallel workers. In watch mode the cache lives in memory for the life of the process.

03 — Memory: arenas, not allocations

One arena per worker. One reset per file. Not thousands of frees.

Every parsed file's AST — nodes and strings — lives in a bump arena (oxc's allocator). Nothing is allocated per node, and message strings are borrowed from the arena until aggregation. Each extraction worker reuses its arena across files with a single reset(): one deallocation per file instead of one per AST node. The napi boundary follows the same philosophy — one native call carries a whole extract, so allocation and copy costs are paid per workflow, not per message.

Shape of crates/palamedes/src/extract.rs
// one arena per worker, reused across files
thread_local! ARENA: RefCell<Allocator>

for file in worker_files {
  let ast = parse_in(&arena, source)
  collect_messages(ast)  // borrowed, zero-copy
  arena.reset()          // one free, not thousands
}

SIMD, honestly

Byte scanning in the lexer is SIMD-accelerated — memchr inside the oxc parser. Palamedes' own crates contain no hand-written SIMD, and this page will not pretend otherwise. If a profile ever shows a hot loop that wants it, the ADR will say so first.

04 — Parallelism that had to be earned

Naive parallelism made it slower. So we profiled the kernel.

Handing 1,500 files to a per-core thread pool made extraction 1.6× slower than running it serially. The profile (samply, 10 kHz) showed why: at twenty workers, 92.8% of samples sat in mach_vm_protect — kernel virtual-memory setup serialized on the process-wide lock. A one-shot CLI pays that setup on every run and never reaches the steady state that would repay it.

Workers12481220
Extraction119 ms69 ms45 ms70 ms151 ms197 ms

The answer is a bounded pool of four workers — the measured floor of that curve, deliberately a constant rather than a function of core count, configurable and clamped. Extract phase: 122 ms → 53 ms. Aggregation stays serial and in input order, and a test proves catalog equality at 1, 2, 4, and 8 workers.

What didn't move the number

Thread-local arenas with reset, mimalloc as global allocator, with_min_len chunking, 128 KB worker stacks — all built, all measured, none explained the curve. Only the worker count did. The arena stayed because it is the right memory shape; mimalloc did not ship. It's all written down.

05 — One catalog engine

ferrocat: catalog semantics live in exactly one place.

Parsing, updating, auditing, ICU diagnostics, PO/FCL storage, and semantic merging are one Rust engine — not a family of plugins that agree most of the time. An audit result cannot depend on which side of the toolchain asked. The same engine is the Git merge driver, so catalog conflicts resolve by meaning, not by line.

CI gate — machine-readable audit (illustrative)
$ pmds extract --check --json
{ "catalog": "src/locales/de.po",
  "missing": 3, "stale": 1,
  "icu": [{ "issue":
    "plural: missing 'other' branch" }] }
Git merge driver — semantic, not line-based
$ git config merge.palamedes-catalog.driver \
  'pmds catalog merge-driver %O %A %B %A \
   --path %P --conflict-strategy=use-first'

06 — The typed boundary

The TypeScript types are generated from the native surface. They cannot lie.

The JS/Rust boundary is crossed per workflow, not per message — one native call runs a whole extract, not 6,000 little ones. And the public TypeScript types are derived from the native binding surface at build time, so the types you code against are the binding, not somebody's memory of it.

07 — Thin adapters, by contract

Adapters render module source. They never touch catalog semantics.

A framework adapter's whole job is to hand compiled catalog artifacts to its host as module source — Next.js gets what Next.js expects, Vite gets what Vite expects. Extraction, identity, and ICU behavior are physically out of reach for adapter code, which is why 25 example apps across six frameworks can behave identically.

08 — One runtime contract

getI18n() everywhere — request-scoped on the server, fixed per document in the browser.

On the server, the active instance rides an AsyncLocalStorage request scope — two concurrent requests in different locales cannot bleed into each other, including through React Server Components. In the browser, the locale is fixed for the life of the document: switching locale is a navigation, never a half-translated page.

Server — request scope
await runWithI18n(reqI18n, () =>
  renderApp()
) // concurrent requests, isolated locales
Anywhere — one call
const i18n = getI18n()
// server component, client island,
// or Express handler — same contract

09 — The machine that checks the marketing

This website fails its build when the numbers drift.

The benchmark figures quoted across palamedes.dev are hardcoded constants — deliberately. A build-time guard parses the checked-in benchmark report and fails the site build if any quoted number no longer matches it. A new benchmark run forces every marketing claim to be updated consciously, or the site does not ship.

$ node scripts/verify-site-bench-data.mjs
✗ bench.ts BENCH_REALISTIC.rows[0].medianMs = 83.89
  report benchmarks/e2e-workflow/results/latest.md says 79.41
✗ site build refused — update the constants (and the prose quoting them)
Why this exists

The same discipline runs the other way: 25 example apps are smoke-checked on PRs, 21 run the full Playwright flow weekly, and the screenshots on this site are versioned browser output. The marketing is downstream of CI — not the other way around.
