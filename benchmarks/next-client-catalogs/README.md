# Next client catalog comparisons

`generate.mjs` and `measure.mjs` compare cold build time and memory for graph
delivery and ADR-030's asset delivery on a generated application.

`runtime.mjs` answers a different question: does ADR-031's permutation delivery
make the same application interactive sooner than ADR-030's assets?

## Run the browser comparison

Build the workspace packages first, then run from the repository root:

```sh
pnpm build
pnpm exec playwright install chromium
node benchmarks/next-client-catalogs/runtime.mjs --runs 20 --warmups 2
```

An existing Chromium executable can be selected with
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, as in the framework contracts. The
harness builds `examples/nextjs-route` twice from the same source, changing
only the delivery option. Both production builds must pass their existing
catalog and relocated standalone contracts before measurement. Each output is
copied to its own temporary deployment and served on loopback. Temporary
servers and deployments are removed when the harness exits.

The comparison uses Next 16.4.1's Turbopack production output and the German
route with four configured locales. It includes the normal example's ticket
panel and a translated FAQ loaded through a lazy import. It does not use the
700-component synthetic build workload.

## Measured boundaries

- `interactiveMs`: navigation start to the first successful translated ticket
  quantity update. The harness clicks as soon as React mounts `ClientReady`
  and observes the change from `1 Ticket` to `2 Tickets`. This includes any
  selective hydration or event replay needed for the translated component;
  the hidden marker alone is not treated as proof of its readiness.
- `interactiveAfterTtfbMs`: the same event, measured after the document's first
  response byte, to separate server timing from client delivery.
- `lazyMs`: FAQ click to insertion of its German content in the DOM.
- `lazyNetworkMs`: FAQ click to completion of its last `/_next/` resource.
  This separates delivery time from React's Suspense reveal timing. The raw
  report retains those lazy resource entries separately.
- `fcpMs` and `ttfbMs`: browser navigation/paint entries, retained to distinguish
  visible server-rendered content from subsequent interactivity.
- `initialStaticBytes`: Resource Timing transfer sizes for `/_next/` resources
  before opening the FAQ, including response headers and encoded bodies. The
  raw report retains each URL path, timing, byte count and cache observation.

All event timings are recorded inside the page with `performance.now()` and
DOM observers. Playwright's polling and assertions are outside those timed
boundaries. A data favicon suppresses the fixture's otherwise implicit missing
favicon request. No request routing is enabled, because Playwright routing
disables HTTP caching.

Each measured pair contains both modes, with AB/BA order alternating. Two
warmup pairs per network profile are excluded. Each mode gets a fresh browser
context for its cold visit, followed by a full document navigation in the same
context for its warm visit. The warm visit therefore also has the first
visit's lazy chunk in the HTTP cache. Server modules and catalogs are warmed
before all measurements. Service workers are blocked, the viewport is
1280 × 900, and there is no CPU throttling.

The profiles are unthrottled loopback and Chromium's simulated 100 ms network
latency with 10 Mbit/s download and 1 Mbit/s upload. They run sequentially in
one browser process. Reports contain medians and interquartile ranges, plus
paired differences and every raw sample. Positive savings mean permutations
were faster or transferred fewer bytes; small differences whose range crosses
zero should be treated as noise.

`results/latest.json` and `results/latest.md` are generated by the harness.
They record source and harness hashes, the source commit and dirty state,
browser/framework/runtime versions, machine information, cache rules, network
profiles and emitted chunk counts. Retain both files when sharing a result.

These are measurements of one local example with warmed Node servers. They
do not establish production/CDN performance, server cold-start cost, behavior
on Vercel, or the benefit for another application's message and chunk layout.
